# Снимки и публикация схемы (Q-6) — отчёт

Версия 1.0 · 23.11.2026 · миграция `0014_schema_snapshots`

## 1. Задача

По ТЗ §3.3 и FR-E-5/FR-E-6: изменения топологии копятся в черновике, администратор
публикует согласованную версию с комментарием, а снимок позволяет открыть состояние
сети на дату, не затирая текущую схему. До этой доработки в системе не было ни
черновика, ни версий: живая схема менялась сразу, «как было на дату» посмотреть было
нечем.

Что вошло в объём:

* фиксация текущего состояния схемы (узлы, порты, связи, блоки, раскладка, штамп);
* список снимков с автором, датой и статусом;
* просмотр снимка в режиме чтения (read-only) и выгрузка JSON;
* публикация версии администратором с фиксацией кто/когда;
* неизменяемость опубликованного снимка.

Что сознательно не вошло (следующий шаг): сравнение двух версий (diff «добавлено /
удалено / переподключено»), печать PDF именно из снимка, удаление черновиков.

## 2. Модель данных

Таблица `gis.schema_snapshots` (схема `gis`, как и остальная топология):

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid, PK | идентификатор снимка |
| `pit_id` | uuid → `gis.pits` (CASCADE) | карьер |
| `title` | varchar(160) | название версии |
| `comment` | text | комментарий энергетика |
| `status` | varchar(16), check `draft` / `published` | черновик или опубликованная версия |
| `payload` | jsonb | полный слепок схемы |
| `created_by` / `created_at` | uuid → `auth.employees`, timestamptz | кто и когда зафиксировал |
| `published_by` / `published_at` | uuid → `auth.employees`, timestamptz | кто и когда опубликовал |

Индексы: `(pit_id, status)` для списка по карьеру и статусу, `created_at` для порядка.

**Слепок (`payload`)** — самодостаточный JSON, не зависящий от текущего состояния БД:

```json
{
  "schema_version": 1,
  "captured_at": "2026-11-23T10:32:00+00:00",
  "pit": { "id": "...", "code": "zapadny1", "name": "Западный №1", "crs_name": "..." },
  "frame": { "sheet_format": "A3", "organization": "...", "object_name": "..." },
  "graph": { "nodes": [ ... ], "edges": [ ... ], "blocks": [ ... ] },
  "counts": { "nodes": 109, "edges": 677, "blocks": 6 }
}
```

`graph` — ровно тот же слепок, что отдаёт редактору `GET /api/topology/graph`
(узлы с портами и координатами, связи с маркой/сечением/состоянием, комплектные
блоки с ячейками и перемычками). Поэтому снимок открывается тем же кодом, что и
живая схема, и не требует отдельной модели представления. Ради этого сборка графа
вынесена из роутера в сервис `app/services/schema_graph.py`: API и снимок строятся
одной функцией и не расходятся.

**Неизменяемость.** У снимка нет эндпоинта изменения. Публикация только проставляет
`status`, `published_by`, `published_at` — тело `payload` не переписывается. Повторная
публикация того же снимка возвращает `409 schema_snapshot.already_published`.

## 3. API

| Метод | Путь | Права | Что делает |
|---|---|---|---|
| `POST` | `/api/topology/snapshots` | `topology.edit` (админ) | зафиксировать текущую схему, `201` |
| `GET` | `/api/topology/snapshots` | любой вход | список снимков (`?status=draft|published`), `published_id` — текущая опубликованная версия |
| `GET` | `/api/topology/snapshots/{id}` | любой вход | снимок целиком, включая `payload` |
| `POST` | `/api/topology/snapshots/{id}/publish` | только `admin` (`require_admin`) | опубликовать версию |

Ошибки — в общем формате проекта: `404` — снимок не найден (или чужой карьер),
`403 perm.denied` — публикация не администратором, `409 schema_snapshot.already_published`
— повторная публикация, `401` — без токена.

Аудит (`audit.audit_log`): `schema.snapshot_created` (с количеством объектов/связей/блоков)
и `schema.snapshot_published` (с названием версии).

## 4. Интерфейс

В панели редактора схемы появилась кнопка **«Снимки»** (рядом с отменой/повтором):

* форма «название + комментарий» и кнопка «Сделать снимок» (видна администратору);
* список версий: название, статус, дата и автор, число объектов/связей/блоков,
  отметка «текущая версия» у последней опубликованной;
* «Открыть» — режим чтения: отдельная read-only копия графа (ReactFlow без
  перетаскивания и выделения), метаданные и выгрузка JSON; живая схема не меняется;
* «Опубликовать» с подтверждением — только для администратора.

Горячие клавиши `Ctrl+Z` / `Ctrl+Y` больше не перехватываются, когда фокус в поле
ввода, `textarea` или `select` — иначе отмена срабатывала при наборе названия снимка.

## 7. Ограничения и следующий шаг

1. **Нет сравнения версий** (FR-E-6 вторая половина): diff «что добавлено/удалено/
   переподключено» между двумя снимками — отдельная задача, данные для неё уже есть
   (`payload.graph` самодостаточен).
2. **Нет PDF из снимка**: печать идёт по живой схеме; для печати версии нужно
   прокинуть `payload` в генератор `schema_pdf`.
3. **Черновики не удаляются** и не чистятся автоматически — накапливаются в списке.
4. **Снимок делает администратор вручную.** ТЗ говорит «изменения копятся в черновике
   автоматически»; сейчас фиксация — осознанное действие. Автоматический черновик
   «на каждое изменение» дал бы сотни записей; если нужно — можно делать один
   авто-черновик на день или по кнопке «зафиксировать перед переключениями».
5. **Опубликованная версия не блокирует правки живой схемы.** По ТЗ публикация —
   фиксация согласованной версии, а не «заморозка»: редактор продолжает работать,
   а расхождение видно по датам снимка и последних изменений.
