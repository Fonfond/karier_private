# Модель оборудования: план переработки (без изменений в коде)

Дата: 26.11.2026 · статус: **проект на согласование** · рабочая БД не меняется
Цель: убрать дублирование «Типы ↔ Реестр», развести классы оборудования и дать отдельные сценарии создания/редактирования, не сломав существующие данные, API, карту и схему.

## 1. Диагноз: почему сейчас путаница

1. **Два источника правды.** В «Типах» админ задаёт `attr_schema`/`required_attrs` (мощность, напряжение), а форма создания в реестре этих полей не показывает — отправляет только имя/тип/статус. Любой тип с обязательными атрибутами даёт `422 «Проверьте атрибуты объекта»` — ровно то, что вы видите при создании КТП.
2. **`category` слишком грубая.** Всего 7 значений (`source, line, equipment, mobile, lighting, aux, pole`), а реальные классы другие: распределительные устройства (ПС/БКРУ), трансформаторные сборки (КТП/ЯКУ-1т/КСР), коммутационные аппараты (ЯКНО/ЯКУ), ячейки, кабели, мобильная генерация. В UI всё сваливается в один список.
3. **Составные объекты не формализованы.** ПС/БКРУ — это блок + ячейки; ячейки создаются через «пачку», роль ячейки — свободный текст `schema_role`, номер/секция — в `attrs` JSON. Модель не знает, что у ПС бывают вводные, секционные и отходящие ячейки, у БКРУ — свои.
4. **Кабель раздвоен.** «Кабель на оборудовании» — это поля связи (`link_type`, `cable_mark`, `cable_no`, `cable_status`), а «кабель в запасе» хранится как связь со статусом `reserve`, хотя связи без двух портов не бывает. Отдельного учёта кабеля как объекта нет.
5. **Нет паспортных данных.** Заводской №, изготовитель, модель, дата ввода, гарантия — всё в `attrs` JSON без валидации и без поиска.
6. **Дубли шаблонов.** Библиотека блоков (`schema_blocks`), `composite_template` типов и «контуры» в редакторе схемы — три механизма для одного и того же.

## 2. Целевая классификация

Ввести `equipment_class` (машинный код) + `group_code` (вкладка UI). Предлагаемое соответствие существующих 19 типов:

| Класс | Вкладка | Существующие типы |
|---|---|---|
`distribution` | Распредустройства (ПС, БКРУ) | `ps_35`, `bkru_1`, `bkru_2` |
`transformer_assembly` | Трансформаторы и сборки | `ktp`, `yaku_1t`, `ksr` |
`switching` | Коммутационные аппараты | `yakno_vozduh_kabel`, `yakno_vozduh_vozduh`, `yaku`, `yaku_vozduh_vozduh` |
`cell` | Ячейки | `yacheyka_2`, `yacheyka_3`, `yacheyka_bkru_2` |
`cable` | Кабели | новый тип `cable` (на оборудовании / в запасе) |
`mobile` | Мобильное и генерация | `generator_benzinovyy`, `generator_dizelnyy`, `dmo`, `mo_machta_osvescheniya`, `motopompa_dizelnaya` |
`line` | Опоры и ВЛ | `op` |
`source` | Питающие центры | `source_35` (Т-1/Т-2), при необходимости |

Класс определяет: набор вкладок, обязательные паспортные поля, сценарий создания (простой / составной / кабель / мобильный), поведение на карте и схеме.

## 3. Изменения БД (только добавления, без удалений)

### 3.1 `gis.asset_types`
+ `equipment_class text not null default 'equipment'` + CHECK по списку;
+ `group_code text` — вкладка UI;
+ `template_version smallint default 2` — версия composite-шаблона.

### 3.2 Новая `gis.asset_type_fields` (вместо `attr_schema`/`required_attrs`)
```
id uuid pk, asset_type_id uuid fk, code text, label text, unit text,
data_type text check (number|integer|text|boolean|date|select),
required boolean default false, default_value jsonb, options jsonb,
min numeric, max numeric, group_label text, sort_order int,
unique(asset_type_id, code)
```
`attr_schema` и `required_attrs` остаются на переходный период и синхронизируются мигратором (двойная запись), затем помечаются deprecated.

### 3.3 `gis.assets`
+ `location_kind text default 'map'` CHECK (`map|schema|warehouse`) — «в запасе» становится явным;
+ `cell_kind text` CHECK (`incoming|section|outgoing|transformer|measurement|lighting|load`), nullable;
+ `cell_no int`, `section_no int` — вместо `attrs.sequence_no/section`;
+ `serial_no text`, `manufacturer text`, `model text`, `commissioned_on date`, `warranty_until date`.

### 3.4 `gis.links`
+ `cable_asset_id uuid null fk gis.assets` — связь ссылается на кабель-объект из реестра (марка/сечение/длина берутся из него; текущие `cable_*` поля сохраняются как денормализация).

### 3.5 Составные объекты
`asset_types.composite_template` v2:
```json
{"sections":[{"no":1,"label":"Секция 1"}],
 "cells":[{"kind":"incoming","count":2,"label":"Ввод","type_code":"yacheyka_2","ports":"standard"},
          {"kind":"section","count":1,"label":"СВ"},
          {"kind":"outgoing","count":6,"label":"Яч. №","type_code":"yacheyka_2"}]}
```
Создание ПС/БКРУ = один вызов `POST /api/assets/{id}/compose` (блок + секции + ячейки за одну транзакцию), а не «контур + пачка вручную». Библиотека блоков остаётся только как пресет раскладки и постепенно скрывается из UI.

### 3.6 Индексы
`assets(asset_type_id)`, `assets(parent_asset_id)`, `assets(location_kind)`, `asset_type_fields(asset_type_id)`, `links(cable_asset_id)`.

## 4. API (обратная совместимость)

Новые/изменённые точки:
* `GET /api/equipment/classes` — классы, вкладки, счётчики;
* `GET /api/asset-types?with_fields=1` — тип + его поля;
* `POST/PATCH/DELETE /api/asset-types/{id}/fields` (admin);
* `POST /api/assets` — валидация по `asset_type_fields`, ошибки в том же формате `fields`/`field_labels`;
* `POST /api/assets/{id}/compose` — создание ПС/БКРУ по шаблону;
* `POST /api/assets/{id}/cells/bulk` — расширить: `cell_kind`, `section_no`, `cell_no`;
* кабели: `GET /api/cables?scope=installed|reserve`, `POST /api/cables` (в запас), `POST /api/assets/{id}/install` (на оборудование → создаёт/привязывает связь), `POST /api/assets/{id}/return`;
* `PATCH /api/links/{id}` — `cable_asset_id`;
* `/api/schema/blocks` — оставить read-only, пометить deprecated.

Старые поля и маршруты не удаляются: старый клиент продолжает работать, новые сценарии включаются флагом `EQUIPMENT_MODEL_V2`.

## 5. UI

1. **«Оборудование»** (вместо «Реестр») — вкладки по классам: Распредустройства / Трансформаторы и сборки / Коммутационные аппараты / Ячейки / Кабели / Мобильное и генерация / Опоры и ВЛ / Прочее. Внутри — привычная таблица с фильтрами по классу, статусу, фидеру.
2. **Мастер создания**: класс → модель (тип) → поля паспорта (динамически из `asset_type_fields`, обязательные помечены) → размещение (карта / схема / склад) → для ПС/БКРУ предпросмотр секций и ячеек → «Создать».
3. **«Модели оборудования»** (админ, вместо «Типы»): конструктор полей (название, единица, тип, обязательность, варианты), порты, состав (секции/ячейки), предпросмотр формы. Оператор эту страницу не видит.
4. **«Кабели»**: две вкладки — «На оборудовании» (связи с кабелем) и «В запасе» (кабель-объекты); действия «Установить» / «Снять в запас».
5. **Карта/схема**: у ячейки бейдж «№ и тип» (вводная/секционная/отходящая); у ПС/БКРУ — свёрнутый блок с числом ячеек; создание ПС — из мастера, а не вручную.

## 6. Как не сломать систему

1. **Только additive-миграции**, ничего не удаляем в первом релизе (колонки, таблицы, маршруты).
2. **Двойная запись** `attr_schema/required_attrs ↔ asset_type_fields` на переходный период, мигратор с проверкой.
3. **Флаг `EQUIPMENT_MODEL_V2`**: новый UI и новые эндпоинты включаются флагом; старые экраны работают.
4. **Обратная совместимость API**: `attrs` принимается по-прежнему; ошибки валидации — в текущем формате 422.
5. **Бэкап + тестовая БД**: миграции прогоняются на `karier_test_db`, проверка up→down→up (тест `test_migrations.py`).
6. **Регресс**: полный `pytest` (сейчас 204 passed) + `tsc/build/vitest` на каждом этапе; новые тесты на классы/поля/кабели/составные объекты.
7. **Данные**: мигратор переносит 19 типов в классы, `attrs.sequence_no/section` → колонки, `required_attrs` → поля; блоки библиотеки → пресеты (без потери).
8. **Фронтенд**: старые ссылки (`/registry`, `/types`) сохраняются как redirect на новые вкладки.

## 8. Что даёт каждый этап

* Этап 1 — больше никаких «создал тип → не могу создать объект»: поля задаются один раз в модели и появляются в форме.
* Этап 2 — привычные вкладки: дизельное, кабели, трансформаторы, распределительные устройства, мобильное; создание по смыслу класса.
* Этап 3 — ПС 35/6 и БКРУ-1 создаются одним мастером (секции, вводные, секционные, отходящие), а не вручную.
* Этап 4 — кабель учитывается как объект: на оборудовании или в запасе, с маркой/сечением/длиной.
* Этап 5 — паспорт: заводской №, изготовитель, дата ввода, гарантия.

## 9. Решения, которые нужны от вас

1. **Кабель**: делаем отдельным объектом реестра (на оборудовании / в запасе) — рекомендую; или оставляем только полями связи, а «запас» — просто статусом?
2. **КСР на санях**: это один объект «КСР с кабелем» или родитель КСР + вложенный кабель?
3. **Паспортные поля**: какие обязательны для каждого класса (например, для КТП — мощность и напряжение; для ДГ — мощность и топливо; для кабеля — марка/сечение/длина)?
4. **ПС 35/6**: одна ПС с двумя секциями и 30 ячейками — это фиксированный шаблон или каждый раз настраивается (сколько вводных/секционных/отходящих)?
5. **Библиотека блоков**: оставить как пресеты раскладки или полностью заменить шаблонами типов?
