# S-8: разделение второго карьера по фидерам от ПС 35-6

**Дата:** 2026-11-25
**Исполнитель:** backend-auditor (задача t14, команда karier-improvements)
**Статус:** реализовано; API реестра и графа схемы фильтруются по фидеру (линии питания), в ответах есть признак фидера. Миграций и изменений данных нет.

---

## 1. Задача и данные

Второй карьер питается от той же **ПС 35-6**, но по другой отходящей линии. В модели «Карьера» фидер — это `gis.lines`, а принадлежность участка сети к фидеру — `gis.links.line_id`:

```
PS-356 ──OUT-1──► PS-356-SEC1 ──► BKRU1-IN1 ──► BKRU-1 ──► BKRU1-OUT1 ──► KTP-14 ...   (ф.21К, main)
PS-356 ──OUT-2──► PS-356-SEC2 ──► BKRU1-IN2 ──► BKRU-1                                  (ф.7К, reserve)
PS-356 ──OUT-4──► POLE-1 ──► POLE-2 ──► POLE-3 ...                                     (ВЛ-6кВ-4 — второй карьер)
```

`gis.lines` содержит `source_asset_id` (не у всех строк заполнен) и `code` (`ф.21К`, `ф.7К`, `ВЛ-6кВ-4`), `kind`, `state`. `links.line_id` заполнен только у 7 связей в демо-данных — в основном «головных» участков фидеров; остальные связи (кабели/шины внутри объектов) идут без линии. Поэтому «объекты фидера» вычисляются обходом, а не одним JOIN.

**Семантика принадлежности объекту фидеру** (реализована в `app/services/topology.py`):

1. Затравка — `to_port` каждой не удалённой связи выбранной линии (первый объект за головным участком).
2. Обход **вниз по потоку**: из объекта идём по его портам `out`/`io` и связям, где этот порт — `from_port`; попадаем в `to_port`-объект.
3. **Не входим в связи, помеченные другой линией** — это граница фидера: объекты второго карьера, подключённые своим фидером, в первый не попадают. Связи без `line_id` считаются продолжением текущего фидера (по ним фидер «доходит» до КТП, ячеек и т.п.).
4. Источник (ПС 35-6) в выборку не попадает, если не является `to_port` линии: он общий для всех фидеров.
5. Объект может принадлежать **нескольким фидерам** — у BKRU-1 основное и резервное питание, поэтому он есть и в `ф.21К`, и в `ф.7К`. Это физически корректно; фронт должен показывать список фидеров, а не один.

## 2. Контракт API

### 2.1. `GET /api/assets` — реестр объектов

Новые query-параметры (взаимоисключающих ограничений нет, приоритет у `line_id`):

| Параметр | Тип | Описание |
|---|---|---|
| `line_id` | UUID | id линии из `GET /api/lines` |
| `feeder` | string, ≤64 | код линии, регистронезависимо, например `ф.21К` |

Поведение:

* **без параметров** — прежнее поведение (все объекты активного карьера, пагинация `limit`/`offset`);
* **известный фидер** — только объекты фидера, `total` считается по фильтру;
* **неизвестный фидер** (`feeder`/`line_id` не найдены) — **200 + пустой список**, `feeder: null`. Выбран осознанно (не 404), чтобы UI-фильтр не ломался при устаревшей ссылке/удалённой линии;
* фильтр комбинируется с `q`, `type_code`, `status`, `is_mobile`, `parent_id`.

Пример:

```http
GET /api/assets?feeder=%D1%84.21%D0%9A&limit=500
```

```json
{
  "items": [
    {
      "id": "d854b457-…",
      "code": "KTP-14",
      "name": "КТП-14",
      "type": {"code": "ktp", "name": "КТП", "category": "equipment", "icon": "▣", "color": "#4C9AFF"},
      "status": "on",
      "grouped": false,
      "feeders": [
        {"id": "b7746264-…", "code": "ф.21К", "name": "Фидер 21К (ПС → БКРУ-1)", "kind": "cable", "state": "energized"}
      ],
      "version": 7,
      "updated_at": "2026-11-03T19:37:24"
    }
  ],
  "total": 42,
  "feeder": {"id": "b7746264-…", "code": "ф.21К", "name": "Фидер 21К (ПС → БКРУ-1)", "kind": "cable", "state": "energized"}
}
```

* `items[].feeders` — список фидеров объекта (пустой, если объект ни к одному не относится, например только что созданный контур).
* `feeder` в корне — фактически применённый фильтр (`null`, если фильтра нет).
* `GET /api/assets/{id}` (и ответы `POST`/`PATCH`/`POST …/state`/`restore`) содержат то же поле `feeders` в `AssetOut`.

### 2.2. `GET /api/topology/graph` — граф схемы

Те же параметры `line_id` / `feeder`.

* **без фильтра** — прежний граф (все узлы/связи/блоки), но у каждого узла появляется `feeders`;
* **фидер** — в `nodes`/`edges`/`blocks` остаются только объекты фидера; связь попадает в ответ, только если оба её конца в фидере;
* **блок** (комплектный объект) остаётся, если в фидер входит **хотя бы одна его ячейка** — иначе блок исчез бы вместе со своими дочерними узлами, которые в `nodes` не выводятся;
* **неизвестный фидер** — `{"nodes": [], "edges": [], "blocks": [], "feeder": null}`;
* в корне ответа — `feeder` (выбранный фидер).

Пример:

```json
{
  "nodes": [
    {"id": "d854b457-…", "code": "KTP-14", "…": "…",
     "feeders": [{"id": "b7746264-…", "code": "ф.21К", "…": "…"}]}
  ],
  "edges": [],
  "blocks": [],
  "feeder": {"id": "b7746264-…", "code": "ф.21К", "name": "Фидер 21К (ПС → БКРУ-1)", "kind": "cable", "state": "energized"}
}
```

### 2.3. `GET /api/lines` — справочник для фильтра

Не менялся: отдаёт `id`, `code`, `name`, `kind`, `state`, `links_count`. Этого достаточно, чтобы построить выпадающий список фидеров и затем передавать `line_id` (или `feeder`).

## 4. Тесты

```
pytest -q tests/test_line_builder.py tests/test_topology_api.py   → 18 passed
pytest -q                                                        → 173 passed   (после канонического reset karier_test_db)
```

Проверяемые сценарии:

1. `?feeder=ф.21К` → в выборке `KTP-14` (вниз по потоку), нет `POLE-3` (другой фидер), у каждого объекта `feeders` содержит `ф.21К`, `total == len(items)`;
2. то же по `?line_id=<id>` — совпадает с фильтром по коду;
3. неизвестный `feeder` и случайный `line_id` → 200, `items=[]`, `total=0`, `feeder=null`;
4. без фильтра — в реестре есть объекты обоих фидеров, `feeder=null`, у `KTP-14` есть `feeders`;
5. граф без фильтра содержит `POLE-3` и `KTP-14`; с `?feeder=ф.21К` — только объекты фидера, все концы связей видимы (узлы + дочерние объекты блоков), `feeders` у `KTP-14` содержит `ф.21К`; неизвестный фидер → пустой граф;
6. только что созданный объект (контур) не попадает в выборку чужого фидера, но доступен по карточке.

**Наблюдение по стабильности тестовой БД (важно для V1 и S-9).** Полные прогоны падали **не из-за кода S-8**, а из-за накопленного мусора в `karier_test_db`:

1. После канонического `C:\karier\test-db-reset.cmd` активных объектов ~585–706. После серии прерванных/параллельных прогонов их стало **1721** (в т.ч. `BKRU-*` — 1220, `SUBSTATION-*` — 501), а перед последним reset — 1950: тесты создают объекты и при падении не убирают их за собой.
2. Хелперы тестов (`tests/test_ux_api.py:15,21` и аналогичные) ищут демо-объекты через `/api/assets?limit=1000`. При раздутой базе сортировка по `code` не отдаёт `KTP-14`/`POLE-3` в первую тысячу → `StopIteration` и каскад падений (29–32 теста), хотя изменения кода ни при чём.
3. Поэтому критерий V1 скорректирован: **два прогона, каждый после канонического reset** test DB (изоляция — задача S-9), а не два прогона подряд без сброса. Дополнительно: не запускать два набора pytest на одной тестовой БД одновременно (`heal_topology` и переключения статусов дают плавающие падения, например `test_power_path_breaks_when_cell_off`).

## 5. Ограничения и что дальше

1. **Один карьер на API.** `GET /api/assets` и граф работают в рамках активного `Pit` (`gis.get_pit`). Разделение второго карьера сделано **по фидерам** внутри этого карьера, как требует S-8. Если второй карьер заведут отдельной строкой `gis.pits`, понадобится выбор карьера в API — это отдельная задача (не входит в S-8).
2. **Общая часть фидеров.** Двойное питание (ф.21К + ф.7К) даёт пересечение объектов: BKRU-1 и его отходящие линии попадают в оба фидера. Это ожидаемо; если фронту нужен «строгий» режим без пересечений — потребуется отдельное правило приоритета (main > reserve), сейчас отдаются все фидеры объекта.
3. **Ответы `/api/schema/...` (place/unplace)** возвращают `AssetOut` с пустым `feeders` — файл `app/api/routers/schema_blocks.py` вне скоупа задачи; при необходимости поле добавляется одной строкой.
4. **Снимки схемы** (`schema_snapshots`) не содержат признака фидера: снимок — это слепок графа на дату, фильтрация выполняется при чтении. Если нужно хранить разбивку в снимке — отдельная доработка.
5. **Производительность.** Принадлежность считается на запрос: один `load_graph` (объекты+порты+связи) и BFS по каждой линии, кеш в `Session.info` на время запроса. На демо-данных (706 активных объектов, 3788 связей, 3 линии) — единицы миллисекунд; при росте до десятков тысяч объектов потребуется материализация (например, `asset_lines` или расчёт при записи).

## 6. Для фронтенда (кратко)

* Список фидеров: `GET /api/lines` → `[{id, code, name, kind, state, links_count}]`.
* Реестр: `GET /api/assets?feeder=<code>` или `?line_id=<id>`; в элементах — `feeders[]`, в корне — `feeder`.
* Схема: `GET /api/topology/graph?feeder=<code>`; в узлах — `feeders[]`, в корне — `feeder`.
* Пустой ответ = «в фидере нет объектов» (не ошибка); неизвестный код — тоже пусто, показывайте «фидер не найден» по `feeder === null`.
* Фильтр можно снимать (запрос без параметров) — поведение реестра и схемы прежнее.
