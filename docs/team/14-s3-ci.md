## 3. `backend-v2/pytest.ini`

```ini
[pytest]
testpaths = tests
addopts =
    --strict-markers
    --strict-config
    --durations=20
markers =
    slow: долгая проверка (> 30 с); такие тесты можно вынести из быстрого локального прогона
    integration: тест требует внешних данных или сервисов (демо-дамп, подложка карты, файлы хранилища) и в CI без фикстур может быть пропущен
```

Почему это важно:

* `--strict-markers` превращает опечатку в маркере в ошибку. Проверено искусственно:
  файл с `@pytest.mark.unknown_marker_xyz` при этом конфиге даёт
  `ERROR ... Failed: 'unknown_marker_xyz' not found in 'markers'`, exit **2** (без флага тест
  молча прошёл бы с warning'ом);
* маркеры объявлены заранее — под S-9 (изоляция тестов) и S-10 (маркировка data-зависимых
  тестов) не придётся менять конфиг;
* `--durations=20` сразу показывает дорогие тесты: в каноническом прогоне самые медленные —
  ~7 с на тест (`test_blocks_s18::test_jumper_inside_block`,
  `test_schema_builder::test_contour_creates_registry_asset_and_block` и т.п.), из-за
  пересоздания блоков/схемы в БД.

## 4. `tests/test_migrations.py`

* **skip, а не падение**, если не задан `TEST_MIGRATION_DATABASE_URL`: причина печатается
  в тексте (`... цикл upgrade/downgrade/upgrade удаляет все таблицы ...`), поэтому
  `pytest -q tests/test_migrations.py` без окружения даёт `3 skipped`, exit 0;
* **защита от опасной базы**: запрещены имена `karier_db`, `karier_test_db`, `postgres`,
  `karier_demo_scratch`; имя базы обязано содержать `migration`;
* три проверки:
  1. `test_single_alembic_head` — ровно одна голова (ловит второй head после мёржа);
  2. `test_upgrade_downgrade_upgrade` — `upgrade head` → есть `gis.assets` → `downgrade base` →
     `gis.assets`/`auth.employees` исчезли → `upgrade head` → ревизия совпала с первой;
     отдельно ограничено время цикла (< 300 с);
  3. `test_autogenerate_has_only_known_drift` — `compare_metadata` (тот же набор схем
     auth/audit/gis/ops, что в `alembic/env.py`) и сверка с `KNOWN_*`;
* **allowlist baseline-дрейфа (S-10)** зафиксирован в самом тесте константами
  `BASELINE_DATE = "2026-11-25"`, `BASELINE_SOURCE` (ссылки на `docs/team/11-v1-acceptance.md` §6
  и `docs/team/13-r2-review.md`, оговорка C1) и `BASELINE_OPS_COUNT = 29`:
  * 4 отсутствующих в моделях индекса — `gis.asset_types.ix_asset_types_parent`,
    `gis.assets.ix_assets_schema_block`, `ops.defects.ix_defects_active`,
    `ops.maintenance_entries.ix_maintenance_at`;
  * 2 внешних ключа, объявленных только в моделях, — `gis.assets(schema_block_id)`,
    `ops.defects(deleted_by)`;
  * 23 комментария таблиц (заданы миграциями, не моделями) — `audit.audit_log`;
    `auth.credentials`, `auth.employees`, `auth.mfa_factors`, `auth.sessions`;
    `gis.asset_moves`, `gis.asset_ports`, `gis.asset_types`, `gis.assets`, `gis.lines`,
    `gis.links`, `gis.map_layers`, `gis.pits`, `gis.schema_blocks`, `gis.switching_ops`;
    `ops.change_log`, `ops.conflicts`, `ops.defects`, `ops.documents`, `ops.inspection_items`,
    `ops.inspections`, `ops.media`, `ops.sync_ops`.

  Тест падает в двух случаях: (а) появилась операция вне списка — новая рассинхронизация
  моделей и миграций; (б) часть списка исчезла (например, после S-10) — тогда baseline надо
  обновить, иначе allowlist «протухнет» молча. Дополнительно проверяется, что в `KNOWN_*`
  ровно 29 операций (`BASELINE_OPS_COUNT`).
  **Пустой autogenerate глобально в этом спринте не требуется** — это S-10; CI валит только
  новые расхождения.

  Как обновлять baseline при легитимных изменениях схемы (например, после S-10):
  1. прогнать `TEST_MIGRATION_DATABASE_URL=<отдельная БД> python -m pytest -q tests/test_migrations.py`
     и посмотреть в тексте падения, какие операции «unexpected»/«vanished»;
  2. если расхождение легитимно (модель приведена к БД миграцией) — убрать/добавить строку
     в `KNOWN_*`, обновить `BASELINE_DATE`, `BASELINE_SOURCE` и `BASELINE_OPS_COUNT`;
  3. если нет — писать миграцию/править модель (обычная работа), baseline не трогать.

## 5. `scripts/check_migrations.sh`

иначе из `tests/.env.test` — как conftest), пересоздаёт одноразовую БД через `psql`,
прогоняет `upgrade head` → `downgrade base` → `upgrade head`, затем

пользователь из DSN. Имя базы обязано содержать `migration`, иначе выход с кодом 2.

### 6.2. Новое расхождение сверх baseline

На отдельной БД `karier_migrations_drift` накатана схема (`alembic upgrade head`) и **в БД
добавлен лишний индекс** `ix_drift_probe_extra` на `gis.assets(code)` — то есть появился дрейф,
которого нет в baseline. Запуск только проверки autogenerate:

```
E  AssertionError: autogenerate показал расхождения вне известного baseline-дрейфа (S-10).
E  Значит модель и миграции разошлись — нужна миграция или правка модели:
E      remove_index:gis.assets.ix_drift_probe_extra

1 failed in 2.94s
```

Нюанс: в полном файле `test_upgrade_downgrade_upgrade` идёт первым и пересобирает схему
(`downgrade base → upgrade head`), поэтому дрейф, внесённый до цикла, стирается — для проверки
детектора запускается именно тест autogenerate на уже подготовленной БД (так же он работает
и в CI: цикл создаёт схему с нуля, после чего сверка идёт на чистой схеме).

## 8. Найденные риски (не блокеры задачи, но важно для CI)

1. **TTL access-токена 15 минут против длинных прогонов.** В одном из прогонов CI-эмуляции
   тест `test_documents_upload_list_and_download` занял 1272 с (аномалия среды), после чего
   сессионный `admin_headers` устарел и ещё 10 тестов упали каскадом с `401 Unauthorized`.
   Полный прогон на канонической базе занимает ~6 минут и укладывается в TTL с запасом, но
   на медленном раннере риск реальный. Лечение (S-9): перелогин по 401 в фикстуре или отдельный
   TTL для тестов.
2. **`pytest-cov` нет в `requirements.txt`** (файл вне inScope): CI ставит его отдельным шагом.
   Локально я поставил `pytest-cov 6.3.0 + coverage 7.17.5` в venv, чтобы проверить команду
   `--cov` (см. таблицу) — сама установка в `requirements.txt` не внесена.
3. **`.coverage` в рабочем каталоге.** `coverage` пишет файл в cwd `backend-v2`. В `.gitignore`
   его нет (файл вне inScope) — при локальных прогонах с `--cov` он будет мусорить в
   `git status`. Предложение владельцу: добавить `.coverage`/`coverage.xml` в `.gitignore`.
4. **`npm ci` локально не выполнялся** (переустанавливает `node_modules`, требует сети; здесь
   уже стоял рабочий `node_modules`). В CI этот шаг обязателен и покроется первым прогоном.
5. **Маркеры `slow`/`integration` объявлены, но пока не используются** тестами — это подготовка
   под S-9: после уборки за собой data-зависимые тесты можно будет помечать и снимать
   `--deselect`-исключения из CI.
6. **`check_migrations.sh` требует bash** (Windows — Git Bash, CI — `/bin/bash`). На машине
   bash из MinGit нет, использовался Git for Windows (`C:\Program Files\Git\bin\bash.exe`).
7. **Ручной `psql` под `karier_user` требует `PGPASSWORD`** (после S-1b для роли включён
   scram-sha-256): без переменной psql висит на запросе пароля. Скрипт `check_migrations.sh`
   это учитывает (`PGPASSWORD`/пароль из DSN), а в ручных проверках администрирование
   выполнялось под `postgres` (local trust).
